# Attribution Smoke V2 采集速度审计

审计输入：

- `zhizengzeng-attribution-smoke-v2.jsonl`
- `zhizengzeng-attribution-smoke-v2.errors.jsonl`

## 结论

本轮计划 40 个请求，成功 33 个、失败 7 个，观测墙钟时间约 22.62 分钟。主要瓶颈不是本地计算，也不只是网络波动，而是“严格串行采集 + 推理型模型消耗大量 reasoning tokens + 空响应的重复重试”叠加。

当前采集器逐个执行请求。33 个成功请求记录的 API 延迟合计 830.35 秒（13.84 分钟）；3 个最终仍为空文本的请求在四次尝试后才失败，额外占用约 498.69 秒（8.31 分钟）。成功后的固定 0.5 秒间隔只占约 16.5 秒，不是主要瓶颈。

## 定量结果

- 成功率：33/40，82.5%。
- 成功请求延迟：均值 25.16 秒，中位数 21.42 秒，P90 63.26 秒，最大 80.26 秒。
- 中文中等长度提示：15 个成功，平均 15.52 秒。
- 英文长文本提示：18 个成功，平均 33.19 秒；本轮一半请求都是长文本，因此会高估正式数据集中只有 25% 长文本时的平均耗时。
- 请求延迟与 completion tokens 的相关系数约为 0.764，说明生成/推理 token 数量是主要延迟来源之一。
- 所有成功记录的 `route_mismatch` 均为 false。

## 失败与无效路由

- `deepseek-v4-pro`、`MiniMax-M2.5`、`MiniMax-M2.7` 的中文请求均在 4 次尝试后返回空文本。这 3 个请求合计消耗约 8.31 分钟。
- `kimi-k2-turbo-preview` 两个请求均返回 HTTP 404，当前路由不可用。
- `mimo-v2-flash` 两个请求均返回 HTTP 400，当前模型或请求参数组合不可用。
- 404 和 400 均不是瞬时网络问题，重新运行不会自然恢复。

## 隐藏推理开销与质量问题

- `gemini-2.5-flash` 两个请求分别消耗 1,470 和 2,950 个 reasoning tokens，最终只得到 107 和 536 个字符，且均以 `finish_reason=length` 结束，不能作为合格训练样本。
- `glm-4.6` 两个请求平均约 70.23 秒，其中 reasoning tokens 分别为 2,961 和 2,087。
- `deepseek-v4-pro` 的英文请求耗时 80.26 秒，3,072 completion tokens 中有 2,181 个 reasoning tokens，并以 `length` 结束。
- `doubao-seed-1-6-flash-250828` 的英文请求包含 3,747 个 reasoning tokens。
- 共 3 个成功响应以 `finish_reason=length` 结束；按照此前的数据质量规则，应标记为截断并排除或定向修复。
- 中文提示的元数据写的是 `400-700 Chinese characters`，实际用户提示要求 `400至500字`，两个长度标准不一致，应在正式采集前统一。

## 规模外推

若完全沿用本轮的串行速度和失败模式，平均每个计划请求约占用 33.93 秒：

- 600 个请求约需 5.65 小时。
- 6,000 个请求约需 56.55 小时。

该估计偏保守，因为本轮长文本占 50%，而正式提示集长文本占 25%；但如果保留会反复空响应的模型，重试损失仍会非常显著。

## 下一步

在扩大到 600 条之前，应先处理模型表和采集器：

1. 删除或替换 `kimi-k2-turbo-preview` 与 `mimo-v2-flash`，不要让确定性 404/400 进入正式任务。
2. 对推理型模型选择可关闭 thinking/reasoning 的可用参数或改用非推理变体；若中转站不支持关闭，则为这些模型单独设置更合理的输出预算和质量规则。
3. 将采集器改为有界并发，建议全局 4 个 worker、同一模型最多 1 个在途请求，保留追加写入、断点续跑和独立重试。
4. 空文本先进行较短、有限的重试；连续空响应应触发模型级熔断，避免每个提示词都等待四轮。
5. 修正长度规范冲突，并把 hidden reasoning tokens、text tokens、`finish_reason` 纳入实时质量审计。

以本轮任务时长粗略估算，4 worker 的无速率限制理论下界约为 5.7 分钟；考虑中转站排队和限流后，更现实的目标是将 40 条控制在约 6–9 分钟。实际加速比需要用同一份 40 请求计划复测确认。
